# ADR-001 — reliable message delivery using rabbitmq and amqplib

**Status:** accepted  
**Date:** 2026-09-20  

## Context

Our order pipeline talks to a warehouse service that is often slow or down for maintenance. We cant just block on a direct http call because if warehouse is down for 10 minutes, our client orders shouldn't fail. So we put RabbitMQ in the middle as a buffer. But just throwing a broker in between doesn't magically make things reliable, and each part of the pipeline had a failure mode that showed up during testing:

- If the queue isnt marked durable, running `docker restart pa2-rabbitmq` wipes the queue completely. even if the queue survives with durable: true, messages without `persistent: true` are lost on restart because rabbitmq only keeps non-persistent msgs in RAM. In demo c, publishing 5 messages with `X-Publish-Mode: fire-and-forget` and killing the broker (`docker kill pa2-rabbitmq`) made messages disappear even though the client already got a 202 response.
- By default `channel.publish()` just puts bytes into the local network buffer and returns a boolean. If we return 202 right away without publisher confirms, the client thinks the order is safe when it actually never made it to disk yet.
- With auto-ack (`noAck: true`), rabbitmq drops the message from the queue the moment it sends it over TCP. If the consumer container crashes while writing to `received.jsonl`, that message is gone forever.
- Also, correlation ids need to be traceable end-to-end. If a client sends an `X-Correlation-Id` header (or if we generate a uuid), it has to follow through from HTTP -> AMQP message property -> consumer log and `received.jsonl`. If it's only printed in one place or put in the wrong field, we lose the trace.

## Decision

We implemented the four required parts in `producer.ts` and `consumer.ts`:

1. In `connectProducerChannel` and `connectConsumerChannel`, we declare the queue `pa2.orders` with `channel.assertQueue(queueName, { durable: true })`. Both sides declare it identically so whichever starts first creates the durable queue.
2. For publisher confirms, in `connectProducerChannel` we use `connection.createConfirmChannel()`. In `publishMessage`:
   - In default "confirmed" mode, we set `{ persistent: true, correlationId: options.correlationId }` and wrap `channel.publish()` in a Promise that only resolves when the broker confirm callback fires. That way `handlePublish` only responds with 202 once the broker confirms it wrote to disk
   - In "fire-and-forget" mode (for demo c), we publish without `persistent: true` and resolve immediately without waiting for confirm.
3. In `connectConsumerChannel`, we added `channel.prefetch(10)` so rabbitmq doesnt flood the consumer memory. In `handleMessage`, we extract `msg.properties.correlationId`, build the JSON object with `receivedAt`, write it to `data/received.jsonl` using `appendFileSync`, log it, and ONLY then call `channel.ack(msg)`. Manual ack is strictly after the write finishes.
4. For correlation id, `producer.ts` validates the incoming header against regex `^[A-Za-z0-9._-]{1,128}$` or generates one with `randomUUID()`. It is passed in AMQP message metadata (`msg.properties.correlationId`) rather than mutating the payload body. The consumer reads `msg.properties.correlationId` and logs it and saves it into received.jsonl.

## Alternatives considered

- Acking before writing to `received.jsonl`: we tested this thought, but if `appendFileSync` fails or consumer dies right between the ack and the write, rabbitmq thinks the message was handled and removes it, leading to silent message loss. Moving ack after the write guarantees at-least-once delivery.
- Relying on `channel.publish()` return boolean: the boolean return from publish only tells you if the write buffer is full or not (backpressure) .It doesn't tell you if RabbitMQ actually received or persisted the message. A broker crash right after still drops the message.
- Auto-ack with low prefetch: while slightly simpler, auto-ack removes messages from rabbitmq before processing completes, so any uncaught exception in consumer drops the message.
- Putting correlationId inside the JSON message body: rejected because it would require parsing and modifying client json payloads, and wouldn't work if payloads are raw buffers or non-json. AMQP message properties are designed specifically for transport metadata
- Using default guest/guest: guest login is restricted to loopback inside container, so management API calls on port 15673 from the host fail. We used the configured `eai:eai-pa2` credentials instead.

## Consequences

- Things are much safer now: orders published with default confirmed mode survive broker restarts (`docker restart pa2-rabbitmq`), and when the consumer is stopped, messages safely pile up in the queue and drain with 0 loss once it restarts (demonstration b)
- Write latency is higher on `POST /publish` because waiting for broker confirm and disk fsync takes more time than blind fire-and-forget publishing.
- If the consumer crashes right after `appendFileSync` but before `channel.ack()`, rabbitmq will redeliver the message on reconnect. Downstream systems need to handle duplicates by checking `correlationId`.
- If the consumer goes down for hours during heavy load, queue depth will keep growing and eat up disk space on the broker. If disk fills up completely, rabbitmq disk alarms will block producers from publishing any new messages.
