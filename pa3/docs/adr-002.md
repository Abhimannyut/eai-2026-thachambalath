# ADR-002 — Splitter correlation, idle-timeout aggregation, partial results, and duplicate suppression

**Status:** accepted
**Date:** 2026-09-28

## Context

Splitting one order into N independent item messages creates four problems that do
not have a single obvious solution:

1. **Correlation** — once the order is split, every downstream message must carry
   enough information for the aggregator to group them back together, even if they
   arrive on different queues, at different speeds, and out of order.
2. **Timeout strategy** — a worker can crash or be stopped while an order is
   in flight.  The aggregator must give up eventually, but not so quickly that
   a legitimately slow but healthy worker triggers a false partial result.  The
   right timeout *shape* (fixed deadline vs. idle reset) matters more than the
   exact number of seconds.
3. **Partial result content** — "not complete" is not useful.  The consumer of
   `orders.complete` needs to know *which* items never arrived so it can retry
   them without re-processing items that already succeeded.
4. **Duplicate suppression** — RabbitMQ delivers at-least-once: if a worker acks
   a message late, the broker can redeliver it.  The aggregator must treat the
   second delivery as a no-op, not as a second item.

## Decision

**Correlation** — The router copies `orderId` into a `correlationId` field and
propagates both on every item message alongside `itemIndex` and `totalItems`.
The aggregator groups by `orderId`.  Keeping both fields (even though they have
the same value at this stage) future-proofs the design: if a gateway later
rewrites `orderId` for multi-tenant routing, `correlationId` remains stable.
Stripping either field in a worker would break aggregation silently — the
aggregator would start a new bucket rather than rejecting the message, which is
harder to diagnose than an outright error.

**Timeout strategy — idle timeout, not fixed deadline** — `in_flight[order_id]`
carries a `last_seen` monotonic timestamp that is reset every time a new (non-
duplicate) result arrives.  A background thread checks every second and evicts
any order that has been idle for `IDLE_TIMEOUT_SECONDS` (default 5 s, read from
the environment so it can be tuned without rebuilding).  A *fixed deadline* from
order creation would misfire on a 50-item order where every worker is healthy and
steadily delivering: if item 49 arrives at second 6 and the fixed deadline is 5 s,
the order is falsely timed out even though all workers answered.  An idle timeout
resets on each arrival and only fires when a worker goes genuinely silent.

**Partial result content** — The partial message includes `itemResults` (every
result that *did* arrive) and `missingItemIndexes` (the sorted list of
`itemIndex` values never seen).  This lets a retry handler re-submit exactly the
missing items without touching the ones already processed, which matters for
idempotency: re-shipping a physical item that was already shipped is more
expensive than skipping it.

**Duplicate suppression** — `in_flight[order_id]['results']` is a `dict` keyed
by `itemIndex`.  Inserting a duplicate is therefore a dict key collision, which
is silently a no-op (`item_index not in state['results']` guard).  This is
cheaper and less error-prone than a separate seen-set, and it falls out for free
from the data structure rather than requiring a second code path.  The `last_seen`
timestamp is deliberately *not* updated on a duplicate so that a flood of
redeliveries cannot keep an order alive past its idle timeout.

All mutable state (`in_flight`) is accessed under a single `threading.Lock`.
The lock is released before any network I/O (`publish_completion`) to avoid
holding it across slow operations.

## Alternatives considered

**Fixed deadline from order creation** — Simpler to reason about (one timestamp
per order, never changes), but fails the 50-item hidden test: a slow but healthy
worker will trip the deadline before it finishes, producing a spurious partial
result.  Rejected in favour of the idle-reset approach.

**Redis for aggregation state** — Would survive an aggregator container restart
mid-order (a known weakness of the in-memory approach).  Adds a dependency and
operational complexity that is not justified at the current scale.  If the
aggregator crashes, the in-flight orders are lost and their timeouts never fire;
the order-api caller would have to retry the whole order.  Accepted as a
documented cost rather than solved with extra infrastructure.

**Dead-letter queue for unknown item types** — When the router encounters an
`item.type` it does not recognise, an alternative is to publish the item message
to a `orders.unknown` dead-letter queue rather than logging and skipping.  This
preserves the message for manual inspection but requires declaring additional
infrastructure.  For this assignment the simpler path (log, skip, let the
aggregator time out with a partial result) is defensible; in production the
DLQ approach would be preferred.

## Consequences

- **Easier**: Adding a fourth item type is a one-line addition to the `ROUTES`
  dict.  Tuning the timeout is an environment-variable change, no rebuild needed.
- **Harder**: The in-memory `in_flight` dict is lost on aggregator restart.
  Any order in progress at the time of the crash will never receive a completion
  message; the upstream caller must implement its own retry or reconciliation.
- **At 10× traffic or 500-item orders**: the `in_flight` dict grows linearly
  with concurrent orders and items; at large scale this needs either a TTL-aware
  store (Redis) or periodic GC.  The single lock becomes a bottleneck if many
  results arrive simultaneously; a per-order lock or a concurrent map would be
  the next step.  Neither is a concern at the current classroom scale.
