# ADR-003 — Multi-source canonical transformation, resilient pricing enrichment, and payment filtering

**Status:** accepted
**Date:** 2026-10-12

## Context

Integrating three disparate source channels (web, mobile, and B2B partner) into a single canonical order model exposed distinct formatting, encoding, and resiliency challenges:

1. **Format and structural divergence**:
   - **Web** (`web-order.json`) uses nested JSON (`customer.address`), standard ISO-8601 timestamps, string statuses, and canonical `PROD-XXX` identifiers, but embeds a nested `customer.payment` card block.
   - **Mobile** (`mobile-order.json`) flattens fields with abbreviations (`oid`, `ot`, `cust_name`, `addr`, `ts`, `st`, `cur`), packs the full address into a comma-delimited string, encodes timestamps as Unix epoch seconds (`ts: 1788258600`), represents statuses as integer enums (`1` for `new`), and encodes currency as ISO 4217 numeric codes (`978` for `EUR`). Payment data is exposed as top-level fields (`pm`, `pan`, `pexp`).
   - **B2B** (`b2b-order.xml`) sends EDI-style XML declaring `encoding="windows-1257"` containing Latvian diacritics (`Anna Bērziņa`, `Rīga`). Parsing this as default UTF-8 silently mangles diacritics into replacement characters (`` or `?`). `fast-xml-parser` uses `@_` attribute prefixes and returns a single object rather than an array when only one `<LineItem>` exists. Additionally, B2B includes untrusted legacy `<UnitListPrice>` elements (`24,99`), unmapped metadata (`ContractDate`, `Notes`), and wire payment details (`IBAN`, `BIC`).
2. **Dynamic pricing and float pitfalls**: Source fixtures do not carry trusted unit prices. Unit prices must be enriched from an external HTTP pricing service (`:4100`). The service returns JSON numbers (e.g., `4.5`), while the canonical schema requires exact two-decimal strings (`"4.50"`). Furthermore, the pricing service can return `404` (unknown product), `500` (server outage), or network errors.
3. **Canonical schema and privacy invariants**: The canonical schema (`canonical/order.schema.json`) enforces `additionalProperties: false` across root, customer, and line item entities. Sensitive payment information (card numbers, IBAN, BIC, expiry dates) must never leak into the canonical representation.

## Decision

We implemented the transformation in [`starter/src/transform.ts`](../starter/src/transform.ts) using the Message Translator, Content Enricher, and Content Filter enterprise integration patterns:

1. **Product ID Normalization (`normalizeProductId`)**:
   - Web: Identity (`PROD-XXX`).
   - Mobile: Prepends `PROD-` to numeric IDs (`001` → `PROD-001`).
   - B2B: Strips `SKU-` prefix (`SKU-PROD-XXX` → `PROD-XXX`).
2. **Exact Decimal Formatting (`toDecimalAmount`)**:
   - Formats numeric prices with `price.toFixed(2)`. This guarantees two fractional digits (`4.5` → `"4.50"`, `22` → `"22.00"`), satisfying the canonical schema regex `^-?[0-9]+\.[0-9]{2}$` without multi-pass float conversions.
3. **Resilient Enrichment (`enrichFromPricing`, `enrichItems`)**:
   - Calls `GET /pricing/:productId` with `X-API-Key: pa4-pricing-key-2026`.
   - On `200 OK`: extracts `unitPrice` (formatted via `toDecimalAmount`), `currency`, and `taxRate`, while retaining source `quantity` and source `productName`.
   - On `404 Not Found`: returns `{ status: "unknown_product" }`, yielding a `UNKNOWN_PRODUCT` warning.
   - On `500` / non-2xx / network failures: returns `{ status: "error", httpStatus }`, yielding a `PRICING_API_ERROR` warning. It never invents fallback prices or zeros.
   - Fault tolerance: individual item enrichment failures do not fail the entire batch. Successful items are retained; failed items generate warnings. If zero items succeed, `order` is returned as `null` to respect the schema's `minItems: 1` requirement.
4. **Encoding and Tolerant XML Parsing (`decodeB2BXmlBytes`, `translateB2B`)**:
   - Reads B2B XML as raw bytes and decodes using Node's `TextDecoder("windows-1257")`, ensuring diacritics are preserved.
   - Normalizes `LineItems.LineItem` to an array regardless of whether fast-xml-parser returns an object or an array.
   - Ignores decorative `<UnitListPrice>` in favor of live pricing. Unrecognized XML elements (`ContractDate`, `Notes`) are discarded by tolerant reader projection.
5. **Timestamp & Enum Normalization**:
   - Normalizes order dates via `new Date(x).toISOString()` (and `epochSecondsToIso` for mobile seconds × 1000) so that identical instants produce byte-identical ISO-8601 strings across all channels.
   - Mapped mobile statuses (`1..4`) and lowercased B2B statuses (`NEW` → `new`).
   - Mapped numeric currency codes (`978` → `EUR`, `840` → `USD`, `826` → `GBP`).
6. **Explicit Content Filtering**:
   - We construct canonical objects through explicit field whitelisting rather than mutating/deleting source properties. Sensitive payment fields (`customer.payment`, `pm`/`pan`/`pexp`, `PaymentDetails`) are excluded at the boundary, ensuring zero payment keys or values leak into output.

## Alternatives considered

- **Failing the entire order on a single unpriced item**:
  - *Rejected*. In high-volume integration pipelines, discarding an entire order because one peripheral accessory failed pricing leads to harsh order abandonment. Emitting `TransformWarning` items while returning valid priced items enables partial fulfillment and downstream exception handling. If no items can be priced, returning `null` safely respects schema validation.
- **Storing monetary amounts as integer cents**:
  - *Rejected*. While integer cents eliminate floating-point representation hazards entirely, the canonical schema is fixed and mandates a decimal string matching `^-?[0-9]+\.[0-9]{2}$`. We conform to the contract rather than altering it.
- **In-memory pricing caching**:
  - *Rejected*. Caching responses would reduce HTTP calls but could serve stale pricing when the catalog price changes at runtime (as verified by `enrichment.test.ts`). Live queries ensure fresh prices.
- **Blacklist field deletion (`delete order.payment`)**:
  - *Rejected*. Blacklists are brittle: if an upstream channel introduces a new payment field (e.g. `cardholder_name` or `cvv`), a blacklist will silently leak it. Explicit construction ensures strict compliance with `additionalProperties: false`.

## Consequences

- **Easier**: Adding future sources requires only writing an input adapter that feeds into the existing `normalizeProductId`, `enrichItems`, and whitelisted construction logic.
- **Harder**: Each line item incurs an individual HTTP request to the pricing service. For orders with large catalogs, sequential or unbatched HTTP requests will increase latency unless batch pricing endpoints are introduced.
- **What breaks first**:
  - If upstream sources introduce product IDs that deviate from known patterns (e.g., alphanumeric UUIDs), `normalizeProductId` will pass them unadjusted, resulting in `UNKNOWN_PRODUCT` warnings if the pricing catalog does not index them.
  - If the canonical schema introduces a new required field, existing translators will fail validation until updated with explicit source-to-canonical mappings.
