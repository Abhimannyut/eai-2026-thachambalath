# ADR-000 — Legacy Fixed-Width and Dual-Encoding File Ingestion

**Status:** accepted
**Date:** 2026-09-10

## Context

The integration processes legacy order exports (`data/orders-20260901.txt`) alongside customer master records (`data/customers.csv`) produced by an upstream department system. The two input files present multiple silent integration challenges:

1. **Dual Encodings:** The customer CSV is UTF-8 encoded, whereas the order file is encoded in Windows CP1257 (`windows-1257`). In Node.js, attempting to read the order file as standard UTF-8 silently corrupts Latvian diacritical characters (e.g. turning `Jānis Bērziņš` and `Šmite` into `J?nis B?rzi??` and `?mite`) without throwing any runtime error, producing a visually plausible but corrupted report.
2. **Fixed-Width Format & Whitespace:** Order records rely on fixed column offsets with left-aligned, space-padded values. Because customer names contain internal spaces (e.g., `Ilze V`), standard token splitting (`line.split(/\s+/)`) breaks layout structure.
3. **Malformed Lines:** Line 6 of the order export is truncated to 26 characters (instead of the required 77 characters). Crashing on this record halts processing of all valid downstream orders, while silently skipping it leads to un-audited data loss.
4. **Data Types & Precision:** Order dates use non-standard `DD.MM.YYYY` formatting, which causes ambiguous date parsing and unwanted timezone offsets if converted via `new Date()`. Monetary amounts use comma decimal separators (`1234,56`, `-250,00`). Routing amounts through `parseFloat` permanently strips precision and trailing zeros (e.g., `"45.20"` becomes `45.2` and `"7800.00"` becomes `7800`).

## Decision

We implemented a robust ingestion handler in `starter/src/ingest.ts` (`ingest()`) following these core design decisions:

1. **Native Character Decoding:** Used Node.js native `TextDecoder("windows-1257")` to decode the raw binary buffer of the order file (`decodeOrderFile()`), eliminating external npm dependencies like `iconv-lite` while accurately preserving CP1257 characters.
2. **Positional Column Slicing:** Defined strict column boundary ranges (`ORDER_LAYOUT`) to slice fields by index (`line.slice(start, end).trim()`), correctly isolating space-padded fixed-width text regardless of internal whitespace.
3. **Non-Blocking Fault Isolation:** Validated every line against `ORDER_LINE_LENGTH = 77`. Truncated or malformed lines are captured in a dedicated `rejected` collection with their 1-based line number (`line: 6`), raw content, and failure reason, allowing processing of valid lines to proceed uninterrupted.
4. **Exact String Manipulations:**
   - **Dates:** Converted `DD.MM.YYYY` strings to ISO-8601 `YYYY-MM-DD` via plain string splitting (`toIsoDate()`), avoiding `Date` object timezone bugs.
   - **Amounts:** Replaced commas with decimal points (`toDecimalString()`) while maintaining monetary values as plain strings, preserving trailing zeros, exact precision, and negative refund amounts.
5. **Set-Based Unmatched Customer Lookup:** Extracted customer IDs from `customers.csv` (skipping the CSV header) and cross-referenced accepted order customer IDs using a `Set` to track unmatched customer master entries (`unmatchedCustomers`).

## Alternatives considered

1. **Third-Party Dependencies (`iconv-lite`, `csv-parser`):**
   - *Rejected:* Node's standard `TextDecoder` natively supports `"windows-1257"`, and simple line/semicolon splitting handles the non-quoted CSV. Avoiding external dependencies keeps the package lightweight and fulfills project constraints.
2. **Regex Parsing vs. Positional Column Slicing:**
   - *Rejected:* Using regular expressions to parse variable whitespace risks misinterpreting padded empty fields or internal spaces in names. Column slicing by exact character offset is deterministic for fixed-width records.
3. **Parsing Amounts with `parseFloat`:**
   - *Rejected:* `parseFloat("45.20")` drops trailing zeros (`45.2`) and loses financial exactness. Storing amounts as decimal strings guarantees lossless round-trip representation.
4. **Throwing Exception on Malformed Records:**
   - *Rejected:* Throwing on line 6 crashes the entire pipeline. Returning a structured `rejected` array provides operational visibility while ensuring valid business orders are successfully processed.
5. **Requesting a Modern JSON/REST API Upstream:**
   - *Considered:* The ideal long-term alternative is negotiating an HTTP REST API with OpenAPI schema validation and UTF-8 JSON payloads from the order team. We accepted file-based ingestion as a legacy constraint for current operations.

## Consequences

- **Easier:**
  - Zero external runtime dependencies.
  - Resilience against partial file corruption; malformed lines do not crash the batch job.
  - Complete audit trail of invalid lines via `rejected[]`.
- **Harder / Risks:**
  - Rigid layout specification: If the upstream legacy system shifts column positions or adds fields, `ORDER_LAYOUT` offsets must be manually updated in code.
  - Character encoding shifts: If upstream operators save `orders-20260901.txt` as UTF-8 by mistake, `TextDecoder("windows-1257")` will misinterpret double-byte sequences.
