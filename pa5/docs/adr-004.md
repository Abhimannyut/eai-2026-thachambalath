# ADR-004 — correlationId in AMQP custom headers, file-backed idempotency, and three-attempt retry with 1 s TTL

**Status:** accepted  
**Date:** 2026-10-12

## Context

Building PA5's fan-out messaging layer forced three concrete choices before the code would even compile correctly:

1. **Where to put correlationId on the wire.** AMQP has a built-in `properties.correlationId` field, but also a general-purpose `properties.headers` map. Both carry arbitrary strings end-to-end.

2. **How many retry attempts to allow and how long to wait between them.** The scaffold configures `MAX_RETRIES=3` and a 1-second TTL on each retry queue. A payment provider going down for thirty seconds would exhaust three attempts in under three seconds—long before it recovers.

3. **Where to store the notification service's "already processed" state.** The natural first instinct is a module-level `Set` in memory, which is three lines of code and zero filesystem dependencies.

## Decision

**correlationId travels in `msg.properties.headers.correlationId`, not in `properties.correlationId`.**  
The native AMQP field is a single opaque string that most brokers neither inspect nor route on; it also gets silently dropped by some middleware layers (e.g. Shovel, Federation) that copy `content` but not every metadata field. A custom header is visible in the management UI alongside `x-death`, survives every dead-letter hop this topology uses, and is explicit in code (`msg.properties.headers?.["correlationId"]`). The canonical order body does not gain a `correlationId` field at all: `additionalProperties: false` in the JSON Schema makes that a validation error, not a convenience.

**Three attempts with a 1-second TTL, as the scaffold provides.** `MAX_RETRIES=3` is kept as-is. The retry TTL is deliberately tight (1 s) because this week's exercise is about watching the DLQ fill, not about building a production SLA. For a real payment provider with a 30-second recovery window, the right answer is an exponential back-off schedule (1 s, 10 s, 60 s) with a separate per-service `MAX_RETRIES`—not a global constant.

**`/data/processed-ids.json` for notification-service's idempotency check, not an in-memory `Set`.** On startup the service reads the file (or creates an empty `[]`), keeps the loaded `Set` in memory for fast lookups, and writes the file back after every new entry. The file is bind-mounted from the host, so it survives `docker compose restart notification-service`.

## Alternatives considered

**`properties.correlationId` (native AMQP field):** Rejected. RabbitMQ's dead-letter mechanism copies the whole message including custom headers but replaces the native metadata fields (`correlationId`, `messageId`) with fresh values in some routing scenarios. Using a custom header guarantees the original value is intact at every consumer, including the DLQ subscriber.

**In-memory `Set` for idempotency:** Rejected for production reasons, accepted as a known trade-off. An in-memory set passes every visible test (no restart happens mid-test) and costs zero filesystem I/O. The concrete failure mode: `docker compose restart notification-service` (or a container crash) empties the set, so the next delivery of an already-logged order is indistinguishable from a first delivery—the customer gets a duplicate notification. The file survives restarts; the set does not.

**`requeue: true` in `channel.nack`.** Rejected. Requeueing sends the message back to the front of the same queue immediately, with no delay and—critically—without incrementing `x-death`. The retry tests check that `x-death` records at least two dead-letter hops before the message reaches the DLQ; `requeue: true` produces no `x-death` entries at all and would fail that assertion.

## Consequences

**Easier:** Tracing a single order across payment, inventory, and notification logs is a single `grep` on `correlationId`—the value is present in every AMQP header and in every log line. The DLQ message carries the original header unchanged, so a human inspector knows exactly which order stalled.

**Harder:** Every consumer that forwards a message must explicitly copy `msg.properties.headers` into the new publish call. A consumer that forgets (e.g. a future forwarding step that only copies `msg.content`) silently breaks correlation for everything downstream—there is no schema enforcement on AMQP headers.

**What breaks first:** If two replicas of notification-service run simultaneously (e.g. during a rolling deploy), both could read the same `processed-ids.json` before either writes back—a classic read-modify-write race. One order would produce two log lines. The file approach is correct for a single-replica service; it is not safe for horizontal scaling without a distributed lock or a proper database.

A legitimately slow inventory service (down longer than 3 × 1 s ≈ 3 s of retry window) routes to the DLQ silently. The order-service has no webhook or callback mechanism to notify the caller; the only way to detect the failure is to poll `orders.dlq` via the management API. That is an accepted cost for this week's scope.
