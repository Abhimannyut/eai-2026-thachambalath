# ADR-005 — Synchronous checkout saga with file-backed idempotency and reverse compensation

**Status:** accepted
**Date:** 2026-10-26

## Context

Building the PA6 checkout orchestrator required solving four concrete integration challenges:

1. **Distinguishing timeout from business error:** Node fetch throws `AbortError` when aborted, but downstream business failures return HTTP 422. Both hit the orchestrator catch block. During initial test runs of shipping delay, timeout threw `AbortError` instead of returning a status. The contract requires HTTP 504 with `code: "timeout"`, whereas step rejection requires HTTP 422. An explicit `isTimeout` indicator was required on the error object before entering compensation.

2. **Asymmetric compensation:** Mock payment exposes `/payment/refund` and inventory exposes `/inventory/release`. Neither shipping nor notification expose rollback endpoints. When shipping timed out after payment and inventory succeeded, the order had to be compensated strictly by releasing inventory and refunding payment.

3. **In-flight idempotency race:** In test 9, a second identical checkout arrived while step 3 was still executing. Reading an `in_progress` record in `idempotency-store.json` forced returning HTTP 409 with `code: "idempotency_conflict"` rather than hanging or returning partial data.

4. **Contract bound enforcement:** Spectral rejected the initial OpenAPI contract because `items` was unbounded. The canonical schema lacked `maxItems`. Linting forced setting `maxItems: 50` in `openapi.yaml`, which `validateCheckoutPayload` then had to enforce in code.

## Decision

We implemented a sequential saga orchestrator in `orchestrator/src/server.ts`:

- **Payload validation and amount derivation:** `validateCheckoutPayload` validates the incoming body against `/canonical/order.schema.json` using Ajv and asserts `items.length <= 50`. `calculateAmount` sums `unitPrice * quantity` as integer cents and formats a two-decimal string ("63.90") passed to payment. Notification receives `order.customer.email`.

- **Timeout handling:** `fetchWithTimeout` wraps fetch with an `AbortController` set to `config.requestTimeoutMs`. If aborted, it tags the thrown error with `isTimeout = true`. The catch block maps this to HTTP 504 and `code: "timeout"`.

- **Sequential execution:** `runStep` executes forward steps sequentially: payment, inventory, shipping, notification.

- **Reverse compensation:** `runCompensation` undoes completed steps in strict reverse order: `inventory_release` first, then `payment_refund`. If any compensation call returns non-2xx or fails, the orchestrator sets `status: "failed"` and emits HTTP 422 with `code: "compensation_failed"`. If all compensation succeeds, status is `compensated`.

- **Idempotency replay:** An incoming key with an identical payload hash replays the cached HTTP status and body from `idempotency-store.json` without re-executing steps. A payload hash mismatch returns HTTP 409 with `idempotency_payload_mismatch`.

## Alternatives considered

- **PA5 choreography versus PA6 orchestration:** In PA5, checkout used choreographed RabbitMQ domain events. Each service acted independently. Choreography decoupled producers and consumers, but lacked atomic rollback coordination and immediate synchronous client feedback. For checkout, orchestration was chosen because the caller requires synchronous completion confirmation, immediate timeout detection, and deterministic reverse compensation across services.

- **Compensating shipping and notification:** We considered adding fake rollback calls for shipping and notification. We rejected this because notification emails cannot be unsent. Treating real-world asymmetric side effects honestly is a core constraint of distributed sagas.

## Consequences

- **Easier:** Tracing any checkout execution order is trivial by inspecting `trace` in `saga-store.json`. Replays are safe and never double-charge.

- **Harder:** Adding downstream steps requires manually updating forward steps, reverse compensation blocks, and OpenAPI bounds.

- **What breaks first:** If the orchestrator process crashes mid-saga, the stored state remains `in_progress`. Any subsequent request with that key receives HTTP 409 indefinitely until manual intervention clears the store. An accepted cost is the lack of automated dead-saga cleanup.
