# ADR-005 — Synchronous saga with file-backed idempotency, timeout-as-abort, and best-effort compensation for non-rollbackable steps

**Status:** accepted
**Date:** 2026-10-26

## Context

Building the PA6 checkout orchestrator forced three concrete decisions before the code was even runnable:

**1. Where in the HTTP lifecycle to distinguish a timeout from a business failure.**
Node's built-in `fetch` throws an `AbortError` when the signal fires; it throws a plain `Error` for network errors; and it returns a non-2xx `Response` for a downstream business failure (e.g. payment declined). All three arrive at the same `catch` block. The contract maps timeouts to `504` + `code: timeout` and business failures to `422`, so a flag (`isTimeout`) had to be attached to the thrown error before the catch block ran compensation — otherwise the same compensation path would emit the wrong HTTP status.

**2. What the saga returns when shipping or notification fails, given that neither has a compensating endpoint.**
The mock services expose `/payment/refund` and `/inventory/release` but nothing equivalent for shipping or notification. A shipping failure after both payment and inventory have succeeded leaves the order in a partially-processed state that can only be compensated by rolling back inventory and payment — there is no "un-ship" call to make. The saga still needs to return a deterministic terminal state, not leave the client waiting.

**3. What the idempotency record must store and how to handle an in-flight race.**
A second request arriving while the first is still mid-saga reads an `in_progress` record in the idempotency store. Returning the first result is impossible (the saga hasn't finished), but hanging or queueing the second request is also wrong. A `409 idempotency_conflict` is the only stateless response that is honest about why the second request was rejected and that gives the client enough information to retry later. The same file that stores the final result also stores the `in_progress` sentinel, so the record survives a container crash and restart.

The contract-first stage changed what I built in one concrete way: the Spectral lint rules forced me to choose a real `maxItems` bound for the `items` array and for the `trace` array before writing any code. Without the lint check I would have omitted those bounds entirely, which would have left the contract vague on a point the README explicitly identifies as a DoS risk.

## Decision

**Timeout detection:** `fetchWithTimeout` wraps `fetch` with an `AbortController` set to `REQUEST_TIMEOUT_MS`. An aborted fetch throws an `AbortError`; the wrapper catches it, attaches `isTimeout = true` to a re-thrown `Error`, and the saga's catch block reads that flag to choose between `504` and `422`.

**Compensation ordering:** `runCompensation` is called for completed steps in reverse order — inventory release first, then payment refund — so that the most recently completed step is undone first. `runCompensation` never throws: it records the outcome to the trace and returns `boolean`. A `false` return from any compensation call sets `compensationFailed = true`, which forces `code: compensation_failed` on the final `422` response. Shipping and notification are never compensated — there is no endpoint to call, and the README explicitly lists compensating them as a common mistake.

**Idempotency store layout:** the file `/data/idempotency-store.json` holds a map from `Idempotency-Key` to a record containing `{ requestHash, state, httpStatus, response, updatedAt }`. On receiving a new request the orchestrator reads the file synchronously, checks the key, and either replays (`state !== "in_progress"`), rejects with `idempotency_conflict` (`state === "in_progress"`), or rejects with `idempotency_payload_mismatch` (hash mismatch). The record is written twice: once with `state: in_progress` before the saga starts, and once with the final state after the saga finishes. Both writes are synchronous `fs.writeFileSync` calls that survive a container restart.

**OpenAPI contract:** `maxItems: 50` on `items` (one saga call per order; 50 items is a reasonable per-order ceiling) and `maxItems: 12` on `trace` (four forward steps + two compensation steps = six; 12 leaves headroom for a fifth step without a breaking change).

## Alternatives considered

**Parallelising independent downstream steps (e.g. shipping + notification in parallel):**
Rejected. The README states "strict sequencing" and the hidden tests verify it by timestamp, not just by trace array order. Parallelising shipping and notification would fail the hidden ordering checks even if the trace array were manually sorted.

**Giving shipping and notification their own compensating endpoints on the mock services:**
This would have made the compensation model symmetric and simpler to reason about — every completed step could be unconditionally rolled back. The mock services are read-only for this assignment, so this was not actually available. But the deeper problem is that "send a notification" is inherently non-transactional: even with a `/notification/cancel` endpoint, the email has likely already been delivered before the cancel request arrives. The asymmetry in the mock design reflects a real constraint: some side effects cannot be undone, and the saga model must accept that.

**Storing only the final response in the idempotency record (no in-progress sentinel):**
This would require the second request to wait on a lock or poll for the first to finish, which introduces blocking or polling complexity that is out of scope for this assignment. A `409 idempotency_conflict` tells the client to back off and retry after a short delay, which is correct behavior for a client that does not know whether its request is lost or in-flight.

## Consequences

**Easier:** Tracing a single checkout across payment, inventory, shipping and notification logs is a single lookup by `orderId` in `/data/saga-store.json`. The `trace` field in the response body contains wall-clock timestamps for every step, so slow downstream calls are immediately visible without grepping container logs.

**Harder:** Adding a fifth downstream step (e.g. a loyalty-points service) requires touching the saga's main try/catch block, the compensation block, and the `openapi.yaml` `maxItems` on `trace`. There is no generic step-registration mechanism — each step is wired explicitly. Two requests for the same `orderId` under different idempotency keys will both attempt the saga independently, and both may try to reserve the same inventory — the mock service does not deduplicate by `orderId`, so the second reservation may succeed even though the first already ran.

**What breaks first:** If `REQUEST_TIMEOUT_MS` is set lower than the mock service's own healthcheck interval (5 s), every step times out even on a healthy stack. The timeout is applied per-step, not per-saga, so a low value multiplied by four steps can make the entire saga reliably fail before the mocks finish initializing. This is an accepted cost — the README uses a default of 2 500 ms which works reliably with the 5 s healthcheck interval in the provided `docker-compose.yml`.
